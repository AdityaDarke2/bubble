PART 0: READ FIRST — CONCEPTS
════════════════════════════════

0.1 Scenario
You are a junior system administrator at a college. The shared FILE SERVER (where students and teachers store files) becomes slow in the evening when many people upload and back up data. Your job is not to guess. Your job is to measure, find the bottleneck, change ONE thing, and measure again.

0.2 Bottleneck
A bottleneck is the slowest resource that limits the performance of the whole system (like a single-lane bridge on a wide highway: no matter how many lanes the highway has, traffic moves at the speed of the bridge). The four main resources are CPU, memory, disk and
network. Buying more RAM will not help if the real problem is a slow disk. Always find the bottleneck first.

0.3 Baseline
A baseline is a set of readings recorded when the system is healthy. You know a person has a fever only because you know the normal body temperature. In the same way, you can say a server is "slow" only by comparing against its baseline.

0.4 The tuning cycle
   1. MEASURE the system
   2. IDENTIFY the bottleneck
   3. CHANGE only one thing
   4. MEASURE again and compare
If you change many things together, you will never know which one
helped.

0.5 CPU: load average and CPU affinity
Imagine a kitchen with 4 chefs (4 CPU cores). Orders are the running tasks. If 4 orders come, every chef is busy and nobody waits. If 8
come, 4 wait in a queue. "Load average" (shown by uptime) is the average number of tasks running or waiting for CPU. uptime shows THREE numbers: the average over the last 1 minute, 5 minutes and 15 minutes. When a heavy load starts, the 1-minute number rises quickly, the 5-minute number rises slowly, and the 15-minute number hardly moves. Comparing the three tells you whether the load is a short spike or a long-running problem. Because these are averages, they never jump instantly to the final value; after one minute of a steady load the 1-minute value has reached only about 60% of it.
"pidstat -u" shows how much CPU each PROCESS is using, so you can find
the culprit.
CPU affinity means "pinning" a process to chosen CPU cores. If a
greedy process is pinned to core 0, it cannot disturb a job running
on core 1. The trade-off: a pinned process cannot use the other cores
even when they are idle, so affinity must be used carefully.

0.6 Memory: RSS, VSZ and limits
RAM is your working desk; the disk is a storage room far away.
For one process, two numbers matter:
   RSS = the physical RAM the process is really using right now
   VSZ = the total virtual memory the process has reserved (can be
         much bigger than what it really uses)
Linux can also set a LIMIT on how much virtual memory a process may
use ("ulimit -v", in kilobytes). If the process asks for more, the
request fails and the program gets a "MemoryError" instead of
swallowing the whole server's RAM. Limits protect a shared server
from one buggy program.
Reminder: check "available" memory (MemAvailable), not just "free",
because Linux uses spare RAM as cache.

0.7 Disk: big files, small files and inodes
Copying 100 MB as ONE file is usually much faster than copying 100 MB
made of thousands of tiny files, because every file needs extra work:
a new directory entry and a new inode (an inode is a small record
that stores a file's information). A filesystem can even run out of
inodes while still having free space; "df -i" shows inode usage. One
common trick is to bundle many small files into a single archive
(tar) before copying or backing them up.
Two numbers to watch in iostat: await (how long a request waits for
the disk, in milliseconds) and %util (how busy the disk is).

0.8 The USE Method
For every resource ask three questions:
   Utilization - how much of it is being used?
   Saturation  - is work waiting in a queue?
   Errors      - are there any errors?
If CPU, memory and disk all look healthy, suspect the network or the
application itself.

0.9 Monitoring tools: Nagios and Zabbix (reading task)
In Lab 7 you used Nagios. A Nagios check is a small program (a
"plugin"). Nagios reads the plugin's exit code: 0 = OK, 1 = WARNING,
2 = CRITICAL, 3 = UNKNOWN, plus one line of text. Zabbix is another
popular open-source monitoring tool. It normally installs a small
"agent" on each server that collects data and sends it to the Zabbix
server, which stores long-term history with built-in graphs. Both
raise alerts when a threshold is crossed. You will answer a question
about this in Part 7.

PART 6: BUILD YOUR OWN MINI MONITOR (SCRIPT WITH ALERTS)
════════════════════════════════
Nagios checks resources and raises alerts. You will build a tiny
version of that, with a DISK alert and a PROCESS alert that names
the culprit.

Step 44. Create the script in your perf-lab-d folder:
   cd ~/perf-lab-d
   nano mini_monitor_d.sh
Paste exactly this:

#!/bin/bash
# Mini monitor D: logs load, disk usage and the top CPU process
DISK_MAX=90
PROC_CPU_MAX=80
echo "time,load1,disk_used_pct,top_process,top_cpu_pct" > perf_log_d.csv
for i in $(seq 1 10); do
  t=$(date +%H:%M:%S)
  l=$(cut -d' ' -f1 /proc/loadavg)
  d=$(df -P . | awk 'NR==2 {gsub("%","",$5); print $5}')
  read pcpu pname < <(ps -eo %cpu,comm --sort=-%cpu | awk 'NR>1 && $2!="ps" && $2!="awk" {print $1, $2; exit}')
  pcpu_int=${pcpu%.*}
  echo "$t,$l,$d,$pname,$pcpu" >> perf_log_d.csv
  if [ "$d" -ge "$DISK_MAX" ]; then
    echo "DISK ALERT at $t: disk is $d% full"
  fi
  if [ "$pcpu_int" -ge "$PROC_CPU_MAX" ]; then
    echo "PROCESS ALERT at $t: $pname is using $pcpu% CPU"
  fi
  sleep 5
done
echo "Done. Data saved in perf_log_d.csv"
